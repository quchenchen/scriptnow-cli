# 接诊与文档化协议

收到翻译或重构需求时，**不立刻读原文、不立刻动手**。先走接诊对话，建立项目索引，再按阶段推进。文档是记忆体，不是副产品——每个阶段的产出必须落文件，新会话优先读文件而不是依赖聊天记忆。

---

## 一、接诊对话（开工前）

### 第一轮：判断路径（1个问题）

收到需求后，先问：

> 「您想做哪种处理？
> - **归化翻译**：保留原故事骨架，调整语言和文化载体，出英文版（读者能认出是哪部中文小说的英文版）
> - **跨文化重构**：以原作为素材，改编成全新品类（狼人/黑帮/吸血鬼等），产出一部全新英文作品（读者认不出原作）
> - **还没想好**：先聊聊原作和目标市场，再决定」

等作者明确回答后，进入第二轮。

---

### 第二轮：按路径深问（6-8个问题，分两组）

**通用问题（两条路径都问）**：

1. **目标市场**：英语哪个市场？（美区Goodnovel / Webnovel / Amazon KU / 英区 / 其他）单章字数有要求吗？
2. **处理范围**：全书翻译，还是先处理指定章节？
3. **交付节奏**：默认**逐章创作，每 5 章合并为一个批次审查稿** —— 单章落 `ch001.md…ch005.md`，第 5 章完成后生成 `ch001-005.md` 合并稿供整批审读；是否沿用这一节奏？还是全部完成再交 / 每章单独确认？
4. **叙事视角（POV）**：默认**全书单一第一人称**，承载角色按题材建议 ——
   - 现言霸总/虐恋/dark romance/狼人/吸血鬼：女主 I-POV（默认）
   - 黑帮：女主 I-POV，若原作为男主权力线强驱动可切换男主 I-POV
   - 校园 YA：按出场权重，一般女主 I-POV
   - 男频升级/系统/修仙：男主 I-POV
   作者可明示：① 坚持原作视角 ② 需要双 POV 整章交替 ③ 改用第三人称有限视角。不默认开双 POV。
5. **保护项**：原作里哪些内容/关系/情感体验是必须保留的？（请用原话描述，我按字面理解，不自行解释）

**路径一·归化翻译追加**：

6. **本地化深度**：全西化（命名/制度/姓氏全部西化，Chen/Liu 等中式姓氏默认改英文姓），还是保留中国背景用英文连载？是否有必须保留华裔身份的角色？
7. **已有资源**：有没有已确定的英文人名、术语表、或参考的竞品？

**路径二·跨文化重构追加**：

6. **目标品类**：具体品类是什么？有没有参考书目（希望像哪本书的风格）？
7. **品类核心卖点**：这个品类读者最期待什么场景？（例：狼人文读者期待 mate bond 触发、mating mark）
8. **改编自由度**：原作情节可以大幅改动，还是核心情节线要保留？

---

### 第三轮：确认并建档（收到回答后）

把第二轮的回答复述一遍，请作者确认：

> 「我来确认一下我们的计划：
> - 路径：[归化翻译 / 跨文化重构]
> - 目标：[平台+ 市场]
> - 范围：[全书 / 指定章节]
> - 交付节奏：[逐章+5章合并 / 其他]
> - POV：[女主第一人称 / 男主第一人称 / 双POV整章交替 / 第三人称有限]，承载角色：[姓名]
> - 本地化深度：[全西化 / 保留背景]
> - 姓氏策略：[全英文姓 / 保留部分华裔姓氏（角色：…）]
> - 保护项：[原话]
> - 第一步：[开始阶段0/步骤①]
>
> 确认无误我就建立项目文件，开始第一步。」

作者确认后，**立即建立项目索引文件**（见下节），再进入工作流。

## 二、项目文件夹与文件命名

### 每本书一个独立文件夹

**项目文件夹名 = 原书名（中文）**。作者第一眼能认出，检索时按原作找。英文书名未定时不用英文名；最终交付时在 05-delivery 里用英文书名。

### 标准目录结构

```
workspace/
└─ [原书名]/					# 项目根；中文书名
    ├─ 00-source/				# 原著与作者参考资料
    │   ├─ 原著.docx / 原著.txt
    │   ├─ 作者备注.md			# 作者口头/文字叮嘱原话
    │   └─ 参考竞品/				# 可选
    │
    ├─ 01-plan/					# 规划阶段产物
    │   ├─ 项目索引.md			# 主索引；每次新会话首先读这个
    │   ├─ 原著分析.md			# 阶段1 / 步骤② 产出
    │   ├─ 世界观决策.md			# 阶段2 / 步骤④ 产出
    │   ├─ 角色档案.md			# 阶段3 / 步骤⑤ 产出
    │   ├─ 大纲.md				# 阶段4 / 步骤⑦ 产出（全书大纲）
    │   └─ 术语表.md				# 全书术语唯一真源（见 continuity.md）
    │
    ├─ 02-outlines/				# 章纲（按卷切）
    │   ├─ 卷1-章纲.md			# 步骤⑧ 产出
    │   └─ 卷2-章纲.md
    │
    ├─ 03-chapters/				# 正文（按批次切）
    │   ├─ ch001-005/
    │   │   ├─ ch001.md
    │   │   ├─ ch002.md
    │   │   ├─ ch003.md
    │   │   ├─ ch004.md
    │   │   ├─ ch005.md
    │   │   ├─ ch001-005.md		# 合并稿（只拼接，不润色）
    │   │   └─ ch001-005-摘要.md		# 本批剧情摘要（给下一批 agent 用）
    │   └─ ch006-010/
    │       └─ ...
    │
    ├─ 04-review/				# 审核产物
    │   ├─ 自检报告-YYYYMMDD.md	# 版本迁移自检产物
    │   ├─ 卷1-审核.md			# 卷级审核
    │   └─ 全书终审.md
    │
    └─ 05-delivery/				# 交付给作者/平台的最终稿
        └─ [英文书名]-v1.0.md
```

### 命名规范

- **项目根**：中文原书名，不加前缀。例：`霸总的替身娇妻/`、`狼王的命定伴侣/`
- **阶段子文件夹**：`NN-stage` 前缀，两位数编号保持排序（00/01/02/03/04/05）
- **批次子文件夹**：`chXXX-XXX`（三位数，前导零）。例：`ch001-005/`、`ch006-010/`
- **正文单章**：`chXXX.md`（三位数）。例：`ch001.md`、`ch127.md`
- **合并稿**：`chXXX-XXX.md`，放在对应批次子文件夹内
- **规划文件**：裸名不加书名前缀（已经在项目文件夹里）。例：`项目索引.md`，不是 `[书名]-项目索引.md`
- **自检/审核报告**：带日期 `自检报告-20261112.md`，防止多次自检覆盖
- **英文书名未定时**：项目根仍用中文书名；交付文件在 05-delivery 用英文名

### 多本书并行

每本书自成一体。两本书同时推进时各在自己的项目文件夹里，术语表/角色档案/合并稿天然隔离，不会撞译名、不会乱 cwd。

### 建档动作

接诊确认后、**进入阶段 1 之前**，agent 执行：

```bash
mkdir -p "[原书名]"/{00-source,01-plan,02-outlines,03-chapters,04-review,05-delivery}
```

然后把作者提供的原著拷进 `00-source/`，建 `01-plan/项目索引.md`。agent 后续所有文件操作在该项目根目录下。

---

### 5 章合并稿

第 5 章完成（通过每章自查清单）后，把 `ch001.md…ch005.md` 正文**无改动**顺序拼成 `ch001-005.md`，放在同批次子文件夹（`03-chapters/ch001-005/`）—— 合并稿只做拼接，不重新润色（避免引入新的 continuity 风险）。文件开头附一段"本批交付说明"：覆盖章节区间、每章章末钩子类型、本批关键决策变更、待确认事项、下批需承接事件。

同目录下再建 `ch001-005-摘要.md` 作为下一批 agent 的衔接资料（见 [批次生产协议](batch-production.md) §四）。

## 三、逐阶段文档交付清单

每个阶段完成后，输出对应文件，更新索引，等作者确认关键节点后再推进。

所有产出相对**项目根**（`workspace/[原书名]/`）给路径。agent 在 cwd = 项目根下操作。

### 路径一·归化翻译

| 阶段 | 产出文件 | 内容摘要 | 是否等确认 |
|------|----------|----------|-----------|
| 0 启动确认 | **建项目文件夹** + `01-plan/项目索引.md` | `mkdir -p` 六个子目录；接诊信息全部写入 | ✓ 等确认 |
| 1 通读分析 | `01-plan/原著分析.md` | 叙事骨架、文化机关清单、待核实项 | 否（继续推进） |
| 2 世界观 | `01-plan/世界观决策.md` | 制度/地名/货币/机关重建决策 | ✓ 等确认（有保护项冲突时必须等） |
| 3 角色 | `01-plan/角色档案.md` | 人名对照表、称谓规则、声线关键词 | ✓ 等确认 |
| 4 大纲 | `01-plan/章节标题对照表.md` | 原标题→英文标题、工作批次 | 否 |

| 6 逐章 | `03-chapters/ch00N-00N/chXXX.md` + 批次末合并稿 `chXXX-XXX.md` | 单章正文串行推进；每完成 5 章出一个合并稿 | 单章否；合并稿 ✓ 等作者整批反馈 |
| 7 审校 | 修订回正文 + `05-delivery/交付说明.md` | 审校报告+修订后正文 | ✓ 等确认 |

## 四、新会话恢复协议

会话中断或跨天继续时，**新会话第一步固定是**：

```
1. 请作者提供项目索引文件路径
   （或在工作区直接找 [原书名]/01-plan/项目索引.md）

2. 读取项目索引，确认：
   - 当前处于哪个阶段
   - 已完成哪些文件
   - 待解决问题清单
   - 下一步是什么

3. 读取下一步所需的相关文件
   （例：准备写ch003，就读角色档案 + ch002结尾 + ch003章纲）

4. 向作者报告：
   「我已读取项目文件，当前进度是 [X]，
    上次完成了 [Y]，
    本次继续 [Z]，请确认。」

5. 作者确认后开工。
```

**禁止**：依赖聊天记忆声称记得设定；问作者「上次说的那个人叫什么来着」；在没有文件依据的情况下声称某个决策已经确定。

## 五、文档更新规则

- **每章完成后**：更新索引里的「当前进度」和「已交付文件清单」
- **有新决策时**：追加到对应决策文件（世界观/角色档案），同时在索引「变更记录」里登记
- **发现前后不一致时**：在「待解决问题」里登记，标明影响章节，不悄悄修改已交付正文
- **作者修改保护项时**：更新索引「作者保护项」，在变更记录里说明旧设定和新设定的差异，回查受影响章节

## 六、文档即记忆体——核心原则

>凡是对后续创作有影响的决策，都必须落文件。
> 凡是没落文件的，视为未决策，不能在正文中悄悄实施。

- 对话里的讨论 ≠ 已确认决策
- 文档里的草稿 ≠ 作者已采纳
- 文件写成功≠ 文学质量通过
- 只有作者明确确认的，才算决策生效
